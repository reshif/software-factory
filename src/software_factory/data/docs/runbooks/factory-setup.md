# Set up the Python factory

Requires Python 3.11+, uv, Git (initialization and missions), and the selected authenticated native client. Node is not a factory dependency.

Install the release wheel with `uv tool install /path/to/software_factory-<version>-py3-none-any.whl`. Then:

```sh
software-factory init /path/to/project --profile claude --dry-run
software-factory init /path/to/project --profile claude --commit
cd /path/to/project
software-factory doctor
```

`init` prints `next_steps`: the exact commands still needed before the first mission, in order, ending with opening the client and running `/factory-build` (Claude Code, Copilot) or `$factory-build` (Codex). The list is empty when only starting the client remains; `start` always names that last step, and `doctor` prints the same `next_steps`.

Choose `codex`, `copilot` or a comma-separated profile list as needed. Existing files and user instruction text are preserved. `--allow-dirty` explicitly allows adoption alongside existing changes. `--skip-sync` installs files without creating the Python environment; hydrate later with `uv sync --locked --no-dev --project .factory`.

`init` detects test commands from project files without running anything and writes them to a new factory.json as required checks: `uv run --locked pytest` (uv.lock), `python -m pytest` (pyproject.toml, requirements.txt, setup.cfg, setup.py, a tests/ directory or test_*.py files), `npm test` (or `pnpm test`/`yarn test` with their lockfile) when package.json has a real `scripts.test`, `go test ./...` (go.mod), `cargo test` (Cargo.toml), and `make test` when a Makefile has a `test:` target (the language runners are then only suggested). The output lists them under `detected_checks`. They have not been run, so run each once and adjust factory.json if needed. When nothing is detected, or with `--no-detect-checks`, factory.json gets the failing configure-me placeholder: replace it with actual required product commands. `inspect` and `doctor` show every suggestion, including package.json lint/typecheck/build scripts, which are never written. Commands are argv arrays with relative working directories. The factory does not run shell expansion. Keep a required check until meaningful tests are configured. Checks and setup steps run with your environment minus `TYPESAFE_API_KEY` by default (`"check_env": {"mode": "inherit"}`). To stop them seeing unrelated credentials, set `"check_env": {"mode": "allowlist"}`: each check then receives only `PATH`, `HOME`, `LANG`, `LC_*`, `TERM`, `TMPDIR`, `TEMP`, `TMP` and `VIRTUAL_ENV` (plus `SYSTEMROOT`, `COMSPEC` and `PATHEXT` on Windows) and the variable names it lists in its own `"env": ["DATABASE_URL", "PYTHONPATH"]`. `PYTHON*` variables are not in the base, so list them if a check needs them. A check with `env` always uses the allowlist, even in inherit mode. `TYPESAFE_API_KEY` is never passed, and listing it is refused. Evidence records each check's mode and the variable names it received (never values), and the gate refuses evidence produced under a laxer environment than factory.json now asks for. The allowlist limits environment exposure only: it is not a sandbox, and checks keep filesystem and network access. After any `factory.json` edit (checks, enforcement, limits and other settings), run `software-factory render`: `factory.lock.json` pins the `factory.json` hash, so `doctor`, `render --check` and the gate report stale exports until it is refreshed. Setup commands (init, upgrade, uninstall, recover, render, auth) and `factory.json` edits are run by a human, not by the orchestrator. Three `factory.json` values are informational: nothing reads `completion_target` (the gate always evaluates READY_PR), `limits.parallel_writers` must stay 1 (it is not a worker count: parallel work runs in lanes, one task per Git worktree, opened by the orchestrator as tasks become ready), and `evidence_exclude` accepts only the built-in metadata exclusions: other entries are rejected, and removing entries has no effect. `init --maintainer NAME` records `owners.maintainer` in a new factory.json. Without it, init uses `git config user.name` (else `user.email`), and leaves it null when neither is set. The readiness gate refuses READY_PR until a maintainer is set. Set `owners.reviewer` yourself; without a maintainer, self-review is not detected, so use a separate reviewer context. Init never rewrites an existing factory.json.

Initialization requires Git, and missions need a commit. `init --commit` (opt-in) runs `git init` on branch main for a plain folder, then commits the installation as "Initialize software-factory" and reports the SHA. In a repository without commits (a plain folder, or one just created with `git init`) it stages everything with `git add -A`, so .gitignore applies (check that nothing private is left unignored), and makes the first commit without needing `--allow-dirty`. In a repository that already has commits it still refuses uncommitted changes, even with `--allow-dirty`, and commits only the factory files on top of the existing history; it never amends. It needs a Git identity (`user.name` and `user.email`) and checks for one before changing anything. Without `--commit`, `init --git-init` creates Git metadata but never commits: commit through normal project workflow (`git add -A && git commit -m "Initialize software-factory"`) before mission execution or JEV assessment.

The installed project owns an exact local Python runtime and uv.lock under .factory. Normal commands dispatch there. Teammates (and each additional worktree) run `uv sync --locked --no-dev --project .factory`, then `uv run --locked --project .factory software-factory doctor`; no global install is required. `.factory/.venv/bin/software-factory` is the same pinned runtime without uv. Sandboxed Codex sessions use it, because the Codex sandbox cannot write the uv cache. `doctor` and `inspect` always run in the invoking process. Every other command refuses to dispatch into the pinned runtime while it reports `runtime_drift`; the error names the drifted files and the fix: `git checkout -- <paths>`, or `software-factory upgrade`, which restores absent or unchanged-upstream runtime files.

Use the native factory-blueprint/build/resume/status prompt. Or inspect deterministic commands with `software-factory mission --help`, `software-factory verify --help` and `software-factory gate --help`. Status is read-only. A build stores the verbatim request (`mission create --request-file`), gathers context, asks ambiguities up front, records AC-n criteria and an architecture diagram, then implements from generated briefs; verification and the review kinds required by the lane (`--kind patch` is the small lane) and `mission risk` come before READY_PR. READY_PR means local evidence is consistent, not attested; remote PR, CI, merge and delivery require their own actual evidence.

New installations use `model_selection.mode: "inherit"`, so startup records one inherited line instead of planning models. Optional keys: `limits.high_risk_lines` (default 400) sets the diff size that makes `mission risk` high, and `enforcement.claude_orchestrator_agent` (default false) exports the opt-in Claude orchestrator agent and guard hook described in [vendor behavior](vendor-behavior.md#enforcement-per-client). JEV ships OFF, with claim assessment in shadow mode. See [model selection](../jev-routing.md) and [claim assessment](semantic-assistance.md). Installation and diagnostics never make inference requests.
