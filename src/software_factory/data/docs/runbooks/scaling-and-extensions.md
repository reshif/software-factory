# Scaling factory work

Use one root installation per monorepo, with check-specific relative working directories. The factory is stack-independent: configure Python, JavaScript, Go, Rust or other product commands explicitly.

One orchestrator owns a mission and one writer owns a workspace. Parallel code writers need isolated workspaces, disjoint contracts and an integration owner: lanes provide exactly that within a mission (`mission lane-open` / `lane-integrate`, one Git worktree per task under `.factory/local/lanes/`, owned paths enforced, the orchestrator integrating). Missions run in parallel in their own worktrees: `software-factory mission create --worktree ...` (run by the user) creates `<repo>.missions/<id>` on a `factory/<id>` branch with its own runtime and mission; open a coding client there, and that session is the mission's one orchestrator. A task cannot start while an active task of a mission in another worktree may touch the same files, so parallel branches do not collide when merged. `mission list --all` shows missions across worktrees; remove a finished mission's worktree with `git worktree remove`. Worktrees separate edits; they are not security sandboxes. State locks live in each worktree's ignored `.factory/local/` and fail fast without waiting, so they do not coordinate across worktrees: two worktrees can create the same mission ID, and keeping one orchestrator per mission across worktrees is operator discipline. Each worktree needs its own `uv sync --locked --no-dev --project .factory`. Give each specialist the brief generated by `software-factory mission brief` (task or review kind); it carries the criteria, constitutional identity, base commit, owned paths, check IDs and result format. Specialists never spawn their own agents.

Persist task results through `software-factory mission record-result` or `record-results`. Reconcile handoff/state/Git after interruption. Attempt limits and unresolved findings remain in force. Registry extensions are reviewed factory-maintenance changes and need schemas, generation tests and native-client smoke checks (see below).

## Controlled content extensions

`.factory/registry.json` lists the content the renderer exports; `.factory/schemas/registry.schema.json` validates it. Extending it is a maintenance mission (it is a protected factory path) with independent review:

- **Roles** (`roles`): each entry has a `name`, `description`, `capability` (`read`, `verify` or `write`, which selects the exported tool set) and the workflow `skill` it preloads. The canonical instructions live in `.factory/roles/<name>.md`. The name `orchestrator` is reserved for the main session and refused as a role.
- **Skills** (`skills`): each name `factory-…` needs `.factory/skills/<name>/SKILL.md` with `name` and `description` frontmatter; the name must match its directory.
- **Entries** (`entries`): each name `factory-…` needs `.factory/prompts/<name>.md` with `name`, `description`, `argument-hint` and `default-prompt` frontmatter. The four core entries (`factory-build`, `factory-blueprint`, `factory-resume`, `factory-status`) are required.
- **Names** are unique across roles, skills and entries together; an entry may not share a name with a skill.

The renderer validates the registry and every referenced file before it writes any export, so an invalid extension changes nothing. Then run `software-factory render`, `render --check`, `doctor` and the [vendor smoke tests](../vendor-smoke-tests.md) for each active client. New native vendor adapters are not a registry extension: they need code and a review of the vendor's official contract.
