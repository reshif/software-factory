# Constitution enforcement map

The [constitution](../../CONSTITUTION.md) (2.1.0) states obligations; this runbook records what, if anything, enforces each one in this release. Cite rules by title: numbers change between versions.

Enforcement layers, strongest first:

- **Gate/CLI:** the state tool refuses a command, or `software-factory gate` (and every transition to READY_PR) fails with a reason. These are deterministic local checks over editable, unattested records: they catch mistakes and shortcuts, not a determined forger (see Honest records).
- **Claude guard (opt-in):** with `enforcement.claude_orchestrator_agent` and `claude --agent factory-orchestrator`, the PreToolUse hook `.factory/hooks/orchestrator_guard.py` denies file-editing tools, non-specialist agents, setup/admin CLI commands, factory subcommand options outside each subcommand's allowlist and shell commands outside a read-only allowlist. Off by default; skipped in untrusted workspaces, `-p` sessions and when hooks are disabled, which the orchestrator's opening self-test detects; live client behaviour not run by this build.
- **Tool restriction:** exported agent tool lists. Claude and Copilot specialists get no agent tool; Claude and Copilot read roles (planner, reviewer) get no edit or shell tool, and the reviewer gets no web tool (Claude `WebFetch`/`WebSearch`, Copilot `web`): it judges the diff and evidence, while the planner keeps web access for documentation research; Codex read roles run with `sandbox_mode = "read-only"`; Copilot's `factory` agent has `read, search, execute, agent`: no edit or web tool, but `execute` remains. Codex has no tool lists, so there these rules are instructions only; Copilot tool lists hold only as far as the selected harness applies them (documented for VS Code Local).
- **Instruction/review only:** the rule is stated in the constitution, roles, skills and generated briefs, and an independent review may catch a breach. Nothing mechanical stops it.

"Partial" below means some cases are checked and others are not; the gap column names what is not.

## Amending the constitution

1. Open a maintenance mission (`mission create --kind maintenance`); only that kind may change protected paths. Record the user's authorization as its scope decision.
2. Classify the change: **MAJOR** removes or redefines an obligation (including renumbering that changes what a cited number means), **MINOR** adds one, **PATCH** changes wording only. Update `Version` and `Last amended`.
3. Record the impact in the mission (spec or plan via `mission record-doc`): changed rules, affected roles, skills, prompts, templates and exports, this enforcement table, and how in-flight missions will be reconciled.
4. Update this table and every document that cites a changed rule by title; run `software-factory render` so exports carry the new constitution hash.
5. Obtain an independent review (protected paths make the mission high risk: code, acceptance and adversarial). The maintenance mission reconciles its own constitution hash as below before READY_PR.

## Reconciling in-flight missions

The constitution change itself is a factory-control change (*Never* rule on factory controls). It lands through a maintenance mission, or on the trunk outside any product mission's diff, for example a `software-factory upgrade` committed on its own. If `.factory/CONSTITUTION.md` changes inside a product mission's candidate, the gate reports "Protected factory path requires a maintenance mission: .factory/CONSTITUTION.md"; that is intended, and reconciliation does not clear it. Reconciliation only rebinds a mission to a constitution that has already landed.

Any pre-merge mission accepted under a different constitution fails its transitions and the gate ("Constitution changed …"), and those errors print the exact commands below. `upgrade` never blocks on this: its report lists each such mission under `missions_needing_constitution_reconcile` as `{id, state, from_version, to_version}`, with a `constitution_reconcile_note`. For each mission, of any kind:

1. Block it: `software-factory mission block --mission ID --reason "Constitution changed; reconciling" --next "Reconcile and re-accept scope"` (active tasks become BLOCKED).
2. Ask the user whether the mission continues under the new constitution. If it does, the user records their approval in their own terminal as an `exception` decision bound to the exact SHA-256 of the new `.factory/CONSTITUTION.md` (the transition error prints this command with the real values):

   ```sh
   uv run --locked --project .factory software-factory mission approve --mission ID --kind exception --subject-hash '<exact new constitution sha256>' --id 'D-CONST-<first 8 hex of the hash>' --reference '<who approved the constitution change, and where>'
   ```

   A decision for any other hash is rejected. If the user does not want to continue, cancel the mission with a reason instead.
3. Run `software-factory mission accept-scope --mission ID`. The scope decision must still match spec.md; if the spec changed, record the user's new acceptance first. Because every open blocker is the constitution-change block, this lifts the hold. The mission returns to PLANNED with tasks TODO; attempts and history are kept, and the mission records the new `constitution_version`.
4. Implement as needed, then a fresh `verify` run, new results and fresh reviews of the required kinds before the gate. Earlier evidence does not carry over.

**Base rebase.** The commit that landed the new constitution (and the re-rendered exports) usually sits between the mission's `base_commit` and HEAD, so without a rebase a product mission's candidate would contain protected factory paths it did not change. During step 3, accept-scope therefore advances `base_commit` to the newest commit C on HEAD's first-parent history for which all of these hold:

- C descends from the old base;
- `git diff <old base>..C` touches only protected factory paths (the policy's `protected_paths` plus the built-in protected floor);
- C's `.factory/CONSTITUTION.md` has the current constitution hash.

It records the move in `base_history` as `{from, to, decision, at}`, naming the `D-CONST-…` decision. Product work committed after C stays in the candidate. If no such commit exists, for example because the constitution change was committed together with product files, or the mission's branch does not contain the commit that landed it, accept-scope refuses, names the offending paths and suggests cancelling the mission and recreating it on the new trunk (`mission transition --mission ID --to CANCELED --reason TEXT`, then `mission create`). Do not rewrite history or edit `base_commit` by hand to get past it.

Missions already MERGED or later keep the evidence they were judged on; do not relabel them.
