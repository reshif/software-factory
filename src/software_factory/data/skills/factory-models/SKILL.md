# Select models for the work

## Inputs and preconditions

Read `.factory/CONSTITUTION.md`, `factory.json`, and the objective or current task. Identify the actual client and harness, billing/provider context, exposed delegation tools and existing user constraints. A Claude model in Copilot still uses Copilot controls. The current main model performs this bootstrap; instructions cannot change their own executing model retroactively.

Use the model runbook, `.factory/docs/runbooks/model-selection.md`, and `.factory/docs/jev-routing.md` for commands, inventory fields, selection controls and result examples. `uv run --locked --project .factory software-factory models --help` lists the model tools. Inspect `jev.enabled` before planning. When enabled, `models plan` asks JEV to choose among eligible candidates; when disabled, it uses the factory-models selector. Discovery, validation, calibration and dispatch remain local metadata operations. Planning and status boundaries from the selected entry remain in force.

## Procedure

1. Establish the task's ambiguity, consequence, codebase breadth, required tools/modalities/context and cost/latency constraints. Use the existing scope; do not infer unlimited spending. Consider stronger reasoning for difficult orchestration and review, efficient models for bounded work, and deterministic tools for checks. Keep the orchestrator's judgment and accountability.
2. Discover the actual client's inventory. Codex has a bounded `model/list` adapter using the supplied native binary. Claude Code has no machine-readable model list: ask the user for the `/model` "Available:" line (or read it when the picker is visible) and run `software-factory models discover --profile claude --session LABEL --picker "<that list>" --client-version <claude --version>`. It keeps only listed aliases that match reviewed guidance, records `user_report` provenance and reports skipped entries; without `--picker` the catalog lists reviewed guidance with unknown availability, which planning rejects. Copilot uses accessible model pickers/host metadata or an explicitly labeled user report. `models plan` refuses an empty catalog, because JEV and factory-models only choose among listed models. Preserve enabled versus unavailable choices, literal IDs, aliases, effort options, lifecycle, provider and operation. Missing metadata stays unknown. An API/CLI catalog is not proof of VS Code account access or subagent eligibility. Never inspect credentials or start inference just to discover a catalog. The factory does not read credentials, but Codex discovery spawns `codex app-server`, which may use Codex's own stored authentication and network access and loads the project's `.codex` configuration.
3. Run `software-factory models sources` and open the relevant current official documentation. Check dated guidance against vendor recommendations. Keep refreshed guidance as local research in the request, not an unsolicited edit of protected canonical recommendations. Run `software-factory models calibration` when local outcome records are available; inspect comparable cohorts and their source references, provenance, sample size and uncertainty. Unknown identity or incomplete comparison hashes do not support a model comparison. Do not fabricate a benchmark ranking.
4. Before planning with `jev.enabled: true`, confirm authorization to send the task objective and any research `strengths` text verbatim to TypeSafe. Keep secrets, credentials, private paths, account identifiers and transcripts out of them. Planning sends compact candidate metadata, not repository source, guidance source lists or files.
5. Use a request template and `software-factory models plan` to intersect task needs, inventory and policy. With `jev.enabled: true`, this is the authorized JEV routing step; it replaces the preference-based selection decision. With `false`, run the ordinary factory-models assessment. Supply `preferred_model` plus a concrete `rationale` when evidence justifies overriding default preference order. Record source links and dates in `research` for newly researched models. Inspect every unresolved assignment and rejected candidate. Unsupported effort, provider restrictions, exact-model requirements and unknown Copilot Local parent cost tiers remain unresolved. Claude subagent selection requires evidenced full native IDs, because main-picker alias resolution does not establish child behavior under a different parent; never silently relax them.
6. Return the model plan with role/task, model/effort, rationale, provenance, fallback and limitations, plus the startup checkpoint (`.factory/docs/runbooks/model-selection.md#startup-checkpoint`): selected, permitted inherited execution with its reason, or unresolved with affected work and missing evidence. Report what was actually checked; invocation alone is not completion. When called by factory-start, return this result to its checkpoint without invoking factory-start again. Standalone model discovery stops here. A blueprint continues independent product specification/planning on the existing session and stops before implementation. Persist planning output only when allowed; explicit read-only requests produce chat output only.
7. For already-authorized execution using selected assignments, register a validated plan with `software-factory mission model-plan`; bind the returned assignment to the relevant task through task-add/task-update. Supply a current catalog when starting/resuming bound tasks. Run `software-factory models dispatch` to obtain supported native settings, then map them to the actual exposed host controls. It is a dispatch report, not an applied setting. Main-session changes use the actual host picker; if unavailable, return to the checkpoint to determine whether inheritance is permitted or the dependent work stays unresolved. Do not edit renderer-owned exports or global settings to force selection.
8. For bound execution, record requested versus observed model and effort from the actual runtime, or `unknown`. Save the observation with the current task result and assignment/attempt hash. Unknown or self-described identity cannot satisfy an exact-model requirement. Handle a substitution explicitly; validate fallbacks against constraints and record its reason. A permitted inherited outcome remains in the checkpoint; do not fabricate an assignment or attach an observation to an unbound task. Independent review still needs a separate context, even when it uses the same model. Optionally record measured outcomes from completed or failed attempts through the runbook's `outcome-record` workflow; keep it metadata-only and never launch additional inference merely to populate calibration.

## Outputs and verification

A dated catalog, a reasoned plan and a checkpoint outcome, with uncertainty visible. Bound execution adds immutable assignment references and per-attempt observations. The state/gate tools validate content hashes and constraints; configuration is not proof of live execution. `factory-status` only reports existing evidence. Cache refresh does not silently change an accepted task assignment.

## Failure behavior

JEV abstention, or a choice below `jev.min_confidence` (default 0.6; reason `low_confidence`), leaves that assignment unresolved in a written plan (exit 0); the user or orchestrator decides it explicitly. A missing key, provider error or timeout exits 2 and writes no plan; transient 408/429/5xx/connection failures are first retried at most twice within the same deadline. Neither case falls back to factory-models; do not silently choose with factory-models while JEV is enabled. Validation and dispatch replay the saved selection without provider calls. Use a cached recommendation only with its age and limitations. Revalidate availability at new sessions/client changes; refresh stale guidance and changed aliases. Diagnose missing context, tooling and implementation defects before changing models. Model reassignment preserves repair attempts. Continue independent authorized work when a particular choice is unresolved; pause that assignment when a hard requirement cannot be met. With JEV disabled, keep inherited execution for unbound tasks when sufficient; do not claim a selected model was used without evidence.

## Optional source assessment

When configured and useful, the main orchestrator may use factory-semantic to assess research claims against supplied vendor excerpts. Honor OFF/shadow and user authority. Semantic support never proves account inventory, actual execution identity, freshness or eligibility; retain discovery and dispatch checks.
