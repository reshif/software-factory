# Upgrade and remove

Invoke the desired release artifact to upgrade, for example `uvx --from /path/to/new-release.whl software-factory upgrade /path/to/project --dry-run`, then remove dry-run after reviewing the plan. `upgrade --to VERSION` (upgrade only) checks that the invoked artifact has that exact version; commands never silently fetch a newer engine. Dependency staging (`uv sync --locked --no-dev`) may download the locked dependencies from the package index; the factory engine itself is never fetched. `upgrade` refuses a downgrade unless `--allow-downgrade` is given.

Three-way comparison uses recorded upstream hashes, proposed release bytes and local bytes. Preserve unchanged-upstream customizations. Conflicting upstream/local changes stop the entire apply. Changes to schemas used by mission history are checked against every persisted record first (see below). Deleting a generated export relinquishes it: `init` and `upgrade` leave it absent and record it as relinquished in `factory.lock.json` (`doctor` only reports it and never writes); `software-factory render` recreates deleted exports. A relinquished file that exists is yours and is never overwritten; `doctor` reports a relinquished entry-point skill (factory-build, factory-blueprint, factory-resume, factory-status) as the error `entry_skill_replaced` when other content occupies it, or the warning `entry_skill_missing` when absent. To restore it, delete the file and run `software-factory render`. Editing a generated export blocks `render`, `upgrade` and `init` until you restore it (`git checkout -- PATH`) or delete it; uninstall gives up ownership of edited exports.

## Schema changes and mission history

When the release changes a schema that persisted records use and `.factory/missions` is not empty, `upgrade` (and `upgrade --dry-run`, which reports the same decision) validates every record against the new release's schema before any write: each `.factory/missions/*/mission.json` (mission schema), `evidence/**/checks.json` (evidence), `results/index.json` and `results/records/*.json` (result index and result), `models/*.json` (model plan), and `factory.json` (factory configuration). A schema the release newly adds is validated the same way only when it governs one of these record types. `factory.json` is validated whenever the factory schema changes, even without missions. When all records validate, the upgrade proceeds and its report lists them under `history.validated_records`. Otherwise nothing is written and the error names each failing file with its first validation error. A changed schema without a known record set also stops the upgrade, as does any symlink under `.factory/missions` (`Symlink in managed path`); replace it with real files or remove it.

Finishing or canceling missions with the old release is not enough, because their records persist in history. A blocked upgrade requires a reviewed data transition: either correct the named records so they satisfy the new schema in a reviewed commit, or move the affected mission directories out of `.factory/missions` (for example to an archive directory) in a reviewed commit, then rerun `upgrade --dry-run`. For example, evidence recorded by 0.2.0 lacks the required `sequence`; set it to the record's 1-based position in the mission's `evidence` list only after reviewing that order, or archive the mission. Missions created before 0.3.0 have no recorded request; they stay valid, keep the earlier gate rules and show the gate warning "legacy mission without recorded request". Blocking review findings recorded without an `id` by earlier releases remain outstanding under the positional id `REVIEW-ID-FN` (1-based position N) until a later review resolves them.

File transactions use preimage checks, private journals and exclusive locks. `software-factory doctor` reports an interrupted operation (`interrupted_transaction`), and until recovery only `doctor`, `inspect`, `status`, `recover`, `auth`, `version` and `--help` run; other commands are refused; `software-factory recover` previews recovery after an interrupted process; `software-factory recover --apply` restores only writes whose current bytes still match that operation. A live process or concurrent edits prevent recovery. Runtime setup failures report the explicit `uv sync --locked --no-dev --project .factory` recovery step.

`software-factory uninstall --dry-run` previews removal. Apply without dry-run to remove unchanged owned assets and sections. Uninstall keeps edited exports and edited factory sections. For an edited section in AGENTS.md, CLAUDE.md or .github/copilot-instructions.md it removes only the two factory marker lines, leaving your text as ordinary content; a later `init` adds a fresh managed section. A `.codex/config.toml` key you changed becomes yours; if it conflicts with what the factory needs, `init` refuses and names the key to change or remove. Preserve other modified content, configuration, history, private records, their ignore rules and provenance. Purging retained state is a separate explicit operation. Restoring an earlier version requires a matched backup of runtime, configuration and records. No destructive Git cleanup is used.

## Constitution changes and in-flight missions

A release can ship a new constitution (0.3.1 ships 2.0.0). Commit the upgrade on its own, outside any product mission's diff: a changed `.factory/CONSTITUTION.md` inside a product mission's candidate fails that mission's gate ("Protected factory path requires a maintenance mission"), by design.

Missions record the constitution hash they accepted, so after such an upgrade every pre-merge mission accepted under the old text stops at its next transition and the gate reports "Constitution changed since mission acceptance"; those errors print the exact reconciliation commands. The upgrade never blocks on this. When the release changes the constitution, its report lists each such mission under `missions_needing_constitution_reconcile` as `{id, state, from_version, to_version}`, with a `constitution_reconcile_note` when the list is not empty (also in `--dry-run`). When the constitution is unchanged, the key is absent. Missions already MERGED or later keep their evidence as judged.

Reconcile each listed mission, whatever its kind:

1. `software-factory mission block --mission ID --reason "Constitution changed; reconciling" --next "Reconcile and re-accept scope"`.
2. Ask the user whether the mission continues under the new constitution; if it does, the user records that approval in their own terminal: `software-factory mission approve --mission ID --kind exception --subject-hash <exact new constitution sha256> --id D-CONST-<first 8 hex> --reference '<who approved the constitution change, and where>'`. If they decline, cancel the mission with a reason instead.
3. `software-factory mission accept-scope --mission ID`: it lifts the reconcile hold, advances the mission's `base_commit` past the commit that landed the new constitution (recorded in `base_history`), returns the mission to PLANNED with tasks TODO, keeps attempts, and records the new `constitution_version`. It rebases only onto a first-parent commit that descends from the old base, differs from it only in protected factory paths and carries the current constitution; otherwise it refuses, names the offending paths and suggests cancelling and recreating the mission. This is why the upgrade must be committed on its own.
4. Run verification, record results and obtain the required reviews again before the gate.

See [constitution enforcement](constitution-enforcement.md#reconciling-in-flight-missions).
